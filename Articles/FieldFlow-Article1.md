Read Only External API for Multi-tenant CRM (and the Authentication Error that Derailed Bots)

Summary: Creating a read only external API for FieldFlow with tenant-specific API keys. Also including fiscal calendar functionality and the authenticating error that caused all my bots to fail on day one. With real examples.

The challenge

A client wanted a Slack bot that could respond to queries such as "what is the status of the Kimba Kempston job?" I agreed and recognised that our API was not designed for this. All APIs require a logged in user’s JWT. However, a bot isn’t a user. It has its own token. This must represent a tenant and be read only – no more.

Although I could have simply added a global API key to existing views, this would have taken a week and involved an unrequired security audit. So I created a new standalone read only API, only for one tenant, using keys starting with `ff_live_`. This is what I did, along with the authentication error responsible for my bots’ day one failure.

In short…

I created a set of four read only APIs. These were: opportunities, opportunity detail, the Vision Dashboard’s projects grid and leads. API keys are generated by, and viewed by, a Tenant Admin within the web application. Data APIs require an API key in either an `Authorization: Bearer ff_live_...` or `X-API-Key` header. Management APIs require a JWT and are restricted to admins only. There is a 240 per minute (40 per 10 seconds) request limit per API key. Dates relate to a tenant’s fiscal calendar (Gregorian or NRF 4-5-4). My error was allowing JWTs on data APIs during initial testing. Then, when I activated the API, bots that had used a login token encountered an immediate `401 invalid_api_key` error as they were using a non-compliant token.

About FieldFlow

I develop FieldFlow – a multi-tenant field service software for roofers and builders. It is constructed using Django 5.2 and Django REST Framework, PostgreSQL 15, Redis 7 and Celery 5.4, all on Python 3.11. The front-end is developed in Next.js 16 (on React 19). Tenant isolation is applied to data. Granular role-based access is also available. This tenant isolation enabled me to introduce the external API, without needing to re-engineer the data.

Requirements

Tenant Admin account

Access to the API host – in production, this is `https://api.repcloud.net`. Locally it is `http://localhost:8000`.

An API key must be generated in the web-app as data APIs will never accept just a JWT.

Two types of authentication

Initially I misunderstood this, so I will explain it clearly.

Authentication type one (for bots) is an API key. It is only applicable to data APIs:

GET /external-api/opportunities/

GET /external-api/opportunities/{id}/

GET /external-api/vision-dashboard/projects/

GET /external-api/leads/

GET /external-api/leads/{id}/

It can be provided as:

```http

Authorization: Bearer ff_live_YOUR_API_KEY

```

Or as:

```http

X-API-Key: ff_live_YOUR_API_KEY

```

Authentication type two (for programmeatic key management) is a JWT. It applies to:

GET /external-api/keys/

POST /external-api/keys/

DELETE /external-api/keys/{id}/

```http

Authorization: Bearer

```

My error was to allow `ff_live_...` and JWTs on different APIs. Specifically, I did not allow `ff_live_...` on `/keys/` and I allowed JWTs on opportunities and leads. I noted this in my documentation after my first error. Prior to this I had even created a test API that accepted both. Unfortunately, ‘convenience’ is often where security debt originates.

Generating an API key

Again, these are generated in the web-application by a Tenant Admin.

1. Login as a Tenant Admin.

2. Go to Admin > Tenant Settings > General > API Keys.

3. Click Generate API Key.

4. Assign a name (such as ‘Slack Bot’) and select ‘Never Expire’ or a date for expiry.

5. Click Generate.

6. Copy the full API key. It is only ever displayed at generation.

Following this, only the start of the key (for example, `ff_live_UrZAx5Xc...`) and related information (status, last usage and expiry) is displayed in a table. Keys can also be manually cancelled here.

Programmatically, keys can be generated via the API host, using a JWT:

```http

POST https://api.repcloud.net/api/v1/external-api/keys/

Authorization: Bearer

Content-Type: application/json

{

"name": "Slack Bot",

"no_expiry": true

}

```

The JSON response contains an `api_key` field. Save this in a secrets management tool. Never commit it.

Data APIs

Most bots access the opportunities API. Each opportunity is included as a separate item. Standard opportunity information is displayed at the head of each entry. Scopes are listed in a `scopes` array. Where a deal involves scopes in Sales, Intake, Production and Closeout, all of these are included in one object.

Each opportunities response also contains a `pipeline_summary` array. Each entry details a stage in the job lifecycle, showing id, name, key, volume and monetary total. This replicates the UI’s job lifecycle board. Thus, a bot can reply to queries such as "how much is sitting in Production right now" without having to calculate a figure from scopes.

The vision dashboard API replicates the internal construction dashboard’s projects grid. Again, each scope is represented in a row. Financial information – revenue, costs, payouts and receivables – is provided. Leads display title, status, source, estimated value, anticipated closing date, account, contact, owner and conversion details.

Date filtering

This was the most time consuming element. Each date can be filtered by specific dates or by a named default. Defaults are translated according to a tenant’s fiscal calendar.

```http

GET https://api.repcloud.net/api/v1/external-api/opportunities/?booked_date_preset=this_month

Authorization: Bearer ff_live_YOUR_API_KEY

```

Defaults include today, this week, this month, this quarter, this year and mtd, qtd, ytd. Additionally there are past_3_weeks and last_30_days, and so on. Within the NRF 4-5-4 fiscal calendar, week, month, quarter and year defaults adhere to a tenant’s fiscal definitions – not civil Gregorian months. This was crucial. For example, a construction business operating on the NRF calendar does not want a bot to refer to ‘this month’ and mean a Gregorian calendar month.

On the vision dashboard API, scopes can also be filtered by their acceptance and rejection dates:

```http

GET https://api.repcloud.net/api/v1/external-api/vision-dashboard/projects/?accepted_at_preset=this_month&page_size=50

Authorization: Bearer ff_live_YOUR_API_KEY

```

Where a filter is applied to accepted and/or rejected scopes, rows with no `accepted_at` value are automatically filtered out.

Throttling

Unlike tenants, data APIs are throttled by API key. Therefore, one tenant’s excessive activity does not affect another’s.

240 requests may be made per minute.

40 requests may be made in any 10 second period.

A Slack slash command generally makes one or two requests. Even a 20 page synchronisation is acceptable. Constant polling (once per second) is also within the throttle. Only highly automated processes approach this level of activity.

Unless `EXTERNAL_API_THROTTING_ENABLED=true`, local development does not involve throttling. Should a tenant exceed the throttle, a `429` HTTP response is returned. Included is a `retry_after_seconds` value and a `Retry-After` header. Clients should pause and then retry using an exponential backoff strategy.

My error

As already noted, I introduced a test API that accepted both API keys and JWTs. This was to facilitate curl-based testing without requiring me to generate an API key. I had planned to delete this test API prior to deployment, but forgot to do so.

On activating my FieldFlow API, all bots that had used a login token began to fail. They received:

```json

{

"error": {

"code": "invalid_api_key",

"message": "A valid API key is required. JWT tokens cannot be used on this endpoint."

}

}

```

HTTP 401. Until then, these bots had functioned in the staging environment as this still allowed JWTs. However, production did not. So I had two issues to address – the continued acceptance of JWTs, and the differing behaviour between staging and production.

Whilst unexciting, the solution was sound. Firstly, I fully removed the test API. Next, I explicitly documented the authentication requirements in error messages. Then I implemented a process to ensure that staging also adhered to the same authentication requirements as production. Finally, I added a section heading above to ensure I never forgot this requirement again.

A further minor error was that, initially, I returned a generic 401 error code. Thus, bots were unable to distinguish between no API key, an incorrect API key and a JWT being used on a data API. I rectified this by introducing three distinct error codes – `authentication_required`, `invalid_api_key` and `authentication_failed`. All are returned within the standard error wrapper:

```json

{

"error": {

"code": "invalid_query_parameter",

"message": "Human-readable explanation.",

"details": {}

}

}

```

Tenant isolation and security

An API key will only retrieve data for the tenant that generated it. There is no tenant cross-access. As the API key is read only, external systems cannot edit or delete data. API keys should be appropriately named and restricted to one integration. Set an expiry date for temporary integrations. Immediately cancel any keys if there is a breach.

An API key is only ever displayed in full at generation. Subsequently, only the key’s prefix is shown. This is intentional. Therefore, even if someone were to take a screenshot of the admin table, a live API key will not be exposed.

Common issues

401 authentication_required – No API key was supplied. Please add an `Authorization: Bearer ff_live_...` or `X-API-Key`.

401 invalid_api_key – An incorrect, expired or cancelled API key was provided. Or a JWT was used on a data API. Confirm the type of token you are providing.

403 – A non-admin tried to administer keys. Either log in as, or utilise a JWT from, a Tenant Admin.

400 invalid_query_parameter – An invalid query has been submitted. This may relate to filtering, date, UUID, boolean, sorting or pagination. See the ‘details’ field for more information.

404 – An item with the specified ID could not be found. Or it belongs to a different tenant.

429 – The throttle has been exceeded. Pause for the number of seconds indicated by `retry_after_seconds` and then retry using an exponential backoff strategy.

500 – An unexpected issue has occurred. Again, retry using an exponential backoff strategy and investigate server logs.

Who should not implement this

If you have just one integration and it is internal then a service account JWT is a more efficient option. However, this external API becomes valuable if numerous external systems require read only access. It is also good practice where individual integrations require separate cancellation facilities. Plus, it is beneficial if clients request a formal agreement. If you are not multi-tenant, you are incurring costs for tenant isolation that you will not utilise.

How I would approach this differently

Definitely, I would not have introduced the test API. Although it only takes 30 seconds to test with a genuine API key, the misalignment between staging and production cost me a morning. Further, rather than documenting the authentication requirements on a wiki page that is unlikely to be consulted, I would have included it at the top of the relevant module.

Next, I plan to implement webhooks. Currently, bots operate by polling. This can make 240 requests per minute. However, rather than bots continually asking for updates, changes should be pushed to them. This is the area I have yet to implement.

I am still undecided on whether throttling should be tenant or API key based. If a client operates numerous bots then, from the platform’s perspective, it is fairer to throttle by API key. However, from the client’s perspective, where they wish to share a budget across their bots, it is fairer to throttle by tenant. For now, I have decided to throttle by API key as I do not want one over-active bot to impact on the activity of others.
